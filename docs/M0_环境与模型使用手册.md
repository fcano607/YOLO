## 2. 检查环境与摄像头

```powershell
python scripts/check_env.py
python scripts/check_env.py --camera-backend DSHOW --camera-index 0
```

脚本核对固定依赖、源码 commit / editable 路径、`pip check`、OpenCV PNG 编解码及随机权重模型 GPU 前向；部署部分只记录导入状态和 provider 声明，实际执行另用第 4 节。

默认每个摄像头后端连续三次打开、各读取三帧并正常释放才算通过，每次限时 15 秒。默认 Windows 依次尝试 DSHOW、MSMF；本机验收通过的是 DSHOW / 索引 0 / native。检查不保存或显示摄像头画面。

| 参数 | 用途 |
| --- | --- |
| `--skip-camera` | 仅检查训练环境及部署状态；摄像头记为未测试 |
| `--camera-timeout 30` | 每次摄像头子进程的时间上限 |
| `--camera-cycles 3` | 同一后端要求连续成功的次数 |
| `--camera-mode mjpeg640` | 诊断时请求 MJPG / 640×480；默认保留设备参数 |
| `--output logs/environment/manual_check.json` | 自定义 JSON 路径 |

每次生成独立 `logs/environment/M0-03_<时间>_snapshot.json`，并更新 [自动检查报告](../reports/environment_check.md)。退出码 0 表示训练与摄像头检查通过；1 表示失败；跳过摄像头且训练通过为 2，非法参数也可能返回 2，需看终端提示。

历史上出现过读帧成功但 `release()` 超时，以及 MSMF 读帧失败。之后两轮正式 DSHOW 连续复开和短时采集通过，但根因没有确定。最小程序也曾复现，OpenCV 4.10 临时对照未解决；现有环境仍使用 4.11.0.86。若复发，先保存失败记录，再检查其他摄像头程序、USB 连接和 Windows 相机的打开 / 关闭表现；长期稳定性留在 M7 验收。

## 3. 使用 E0 预训练实例分割

### 3.1 权重与类别

权重为 `artifacts/pretrained/yolo11n-seg.pt`，6,182,636 字节，SHA256：

```text
55ed65c56c91713d23e8402371c6c49a6fd84f257f7dce452e8d70e41dcbe152
```

下载地址、哈希和参数见 [e0.yaml](../configs/e0.yaml)。模型保留 COCO 80 类，默认推理筛选以下三类，通过实际 `model.names` 查找：

| 名称 | 当前 E0 模型 ID | 后续项目数据 ID |
| --- | ---: | ---: |
| cup | 41 | 0 |
| bottle | 39 | 1 |
| cell phone | 67 | 2 |

当前配置为 640×640、FP32、GPU 0、conf=0.25、NMS IoU=0.7、retina_masks=true。640×640 是经过缩放 / 补边后的模型输入尺寸；FP32 表示使用 32 位浮点数。原始摄像头画面可为 640×480。锁定版本以 `quantize=32` 表示 FP32；这些参数尚未通过正式验证集优化。

### 3.2 常用命令

```powershell
# 校验权重，缺失时下载；从锁定源码恢复公共图片。
python scripts/prepare_e0.py

# 公共图片，显示原模型全部类别。
python scripts/predict_e0.py --source demo/input/E0/bus.jpg --all-classes

# 已保存的桌面图片和视频，默认筛选三类。
python scripts/predict_e0.py --source runs/E0/M0-04_20261002_camera_targets/input_best.jpg
python scripts/predict_e0.py --source runs/E0/M0-04_20261002_camera_targets/input.mp4

# 摄像头：会保存原始画面与结果，窗口按 Q / Esc 或到期退出。
python scripts/predict_e0.py --camera --seconds 10 --show
```

`--source` 与 `--camera` 互斥；相对路径从项目根目录解析。还可使用 `--max-frames 100`、`--camera-index 0`、`--conf 0.25`、`--output runs/E0/<新名称>`。已有输出目录拒绝覆盖。`--device cpu` 是脚本支持的选项，本次 E0 验收实际使用 GPU。摄像头先初始化 GPU，再开启采集；工作进程受超时限制。

### 3.3 输出怎么看

默认每次保存到新的 `runs/E0/<时间戳>/`：

| 文件 | 内容 |
| --- | --- |
| `summary.json` | 参数、设备、版本、类别映射、帧数、退出与释放状态 |
| `frames.jsonl` | 每帧框、置信度、类别、mask 面积及输出信息 |
| `input_first.jpg` / `result_first.jpg` | 第一帧输入 / 结果 |
| `input_best.jpg` / `result_best.jpg` / `best_frame.json` | 框数最多的示例帧与预测数值；best 不表示精度最好 |
| `input.mp4` / `result.mp4` | 视频或摄像头输入 / 结果；单张图片不生成视频 |
| `worker.log` | 摄像头进程日志；失败时另存诊断记录 |

视频采用 mp4v。设备报告 FPS=0 时按配置的 30 FPS 回退写入，因此编码时间轴与墙钟可能不同。成功退出码为 0，运行失败为 1，参数错误看终端。`passed` 说明链路运行和保存成功；confidence、预测次数与帧数不能作为准确率、mAP 或正式 FPS。

现有演示和原始画面见 [M0 验收报告](../reports/M0_阶段验收报告.md#3-e0-运行与效果观察)。

## 4. ONNX 与 TensorRT 部署预检查

这是 M0-05 的兼容性预检查；完整 M5/M6 的独立预处理、后处理、精度与测速继续按任务开展。

```powershell
python scripts/check_deployment.py
```

配置见 [deploy-precheck.yaml](../configs/deploy-precheck.yaml)，当前引用 M0-04 已保存的公交车图和桌面图。全部检查依次在限时子进程执行 export、ORT CPU、ORT CUDA、TensorRT；时间上限分别为 300、120、120、600 秒。

```powershell
python scripts/check_deployment.py --stage export
python scripts/check_deployment.py --stage ort_cpu
python scripts/check_deployment.py --stage ort_cuda
python scripts/check_deployment.py --stage trt
```

后三项依赖已有 ONNX 和同一次导出的参考数组。更改输入或配置后重新执行全部阶段。完整成功需看 [部署汇总](../logs/deployment/M0-05_summary.json) 的 `all_backends_passed=true` 与 `same_artifacts_verified=true`。

| 内容 | 当前接口 / 位置 |
| --- | --- |
| 导出参数 | batch1，640，FP32，opset17，dynamic=False，simplify=False，nms=False |
| 输入 | `images [1,3,640,640]`，float32 |
| 输出 0 | `[1,116,8400]`，4 个框坐标 + 80 个类别分数 + 32 个 mask 系数 |
| 输出 1 | `[1,32,160,160]`，实例分割原型 |
| 模型与数组 | `artifacts/precheck/M0-05/` |
| 执行 / 构建证据 | `logs/deployment/` |

脚本保存 LetterBox、BGR→RGB、NCHW、float32 / 255 后的输入，以及 PyTorch CUDA FP32 参考输出，再给各后端使用同一张量。原始输出逐元素对照 `atol=1e-3, rtol=1e-4`；完整框和 mask 后处理尚未单独部署。

重复执行会更新配置所指定的模型及报告目录。需要保存新实验时，复制配置并修改 `output_dir` / `report_dir`，再通过 `--config <新配置>` 运行。

ORT CUDA 进程先导入 torch 加载 CUDA / cuDNN DLL，再创建 CUDA session，并通过 profile 核实实际 GPU 节点执行。TensorRT 直接使用 Python API 和 GPU 缓冲，读取 ONNX bytes 后 `parser.parse(bytes)` 避开中文路径问题。原生 engine 没有 Ultralytics 元数据头，使用本项目接口读取。本次未验证 ORT TensorRT EP，也没有完全移除运行时 torch。

TensorRT 11 本次采用强类型 FP32 并关闭 TF32；FP16 后续另做。engine 依赖 GPU、平台和 TensorRT 版本，移机需重新构建并验收。`tmp/deploy_wheels/` 仅是已安装运行库的下载缓存，删除后若要离线重装需重新取得安装包；现有环境从 `D:` 的 site-packages 加载。

## 6. 新项目副本的恢复方案

本机已有环境的新进程复现已通过；Conda 文件解析和当前环境 pip dry-run 已通过。**干净环境重装、另一台电脑运行尚未实际验证。** 以下使用新环境名，以保留现有环境。在 Windows x64、Git、Conda 和兼容 NVIDIA GPU / 驱动条件下，从项目根目录运行：

```powershell
conda env create --name yolo-restore --file environment.yml
conda activate yolo-restore
python -c "import sys; print(sys.executable); print(sys.version)"

python -m pip install --no-deps torch==2.8.0+cu129 torchvision==0.23.0+cu129 --index-url https://download.pytorch.org/whl/cu129
python scripts/setup_source.py
python -m pip install --no-build-isolation -c configs/constraints-runtime.txt -r requirements-train.txt -r requirements-deploy.txt
python -m pip check

python -c "from deploy.paths import load_paths; [p.mkdir(parents=True, exist_ok=True) for p in load_paths().values()]"
python scripts/prepare_e0.py
python scripts/save_environment.py
python scripts/verify_reproducibility.py
```

约束文件不会主动安装全部继承包。先安装固定 GPU torch，再按项目直接需求恢复；基础文件不克隆旧 tf2。TensorRT Windows 运行库下载约 2.1 GiB。更换机器后再运行第 4 节的部署检查；其输入图片须自行提供，或修改配置后重新生成参考。

Git 管理自己的代码、配置、恢复文件、学习文档和小型证据。上游源码由锁定脚本恢复，官方权重 / 公共图片由资产脚本恢复；本机 `artifacts/`、`runs/`、`demo/` 和相机画面需另行备份。未来人工标注、正式训练 best/last 权重及划分清单属于关键资产。本次没有制作整个 Conda 目录的离线二进制备份。
