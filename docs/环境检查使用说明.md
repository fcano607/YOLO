# M0-03 环境检查使用说明

更新日期：2026-10-02。正式检查入口已实现，Python、锁定依赖、源码、OpenCV 与 GPU 检查通过；摄像头读取已证实，但正常释放设备仍有问题，M0-03 保持进行中。

## 1. 这一步解决什么

把环境检查变成可重复运行的命令。以后环境被误切换、依赖被升级或摄像头不可用时，先运行检查，再根据报告处理。

脚本复用 M0-02 的训练检查函数，核对实际解释器、requirements 中的固定版本、源码 tag/commit 与 editable 加载路径，执行 `pip check`、OpenCV PNG 编解码和随机权重 YOLO11n-seg 的 GPU 前向。

部署模块单独记录安装/导入状态；若 ORT 已安装，列出它声明可用的执行 provider。当前 ONNX、ORT、TensorRT 均未安装，登记为 M0-05 待办，不能据此宣称部署通过。

## 2. 使用方法

在项目根目录运行：

```powershell
conda activate yolo
python scripts/check_env.py
```

默认检查摄像头索引 0；Windows 下依次尝试 DSHOW、MSMF，每种方式最多等待 15 秒。每次仅读取三帧，不显示或保存摄像头画面。

也可以明确使用专用解释器：

```powershell
& 'D:\software\anaconda\envs\yolo\python.exe' scripts/check_env.py --camera-index 0
```

只检查训练环境并记录部署状态，暂时跳过摄像头：

```powershell
python scripts/check_env.py --skip-camera
```

| 参数 | 用途 |
| --- | --- |
| `--camera-index 0` | 选择摄像头索引；多个设备时按实际结果调整 |
| `--camera-backend DSHOW` | 只测指定后端；可选 AUTO、DSHOW、MSMF、ANY |
| `--camera-timeout 30` | 每个摄像头子进程最多等待 30 秒 |
| `--camera-mode mjpeg640` | 诊断时请求 MJPG / 640×480；默认 native 保留设备默认参数 |
| `--skip-camera` | 记录摄像头未测试，M0-03 保持未完成 |
| `--output logs/environment/manual_check.json` | 指定 JSON 输出路径；相对路径从项目根目录解析 |

摄像头在独立子进程中检查。驱动调用阻塞时终止该子进程，主检查程序继续保存已获得的结果；不能将超时前读帧成功误记为正常关闭设备。

## 3. 产出和退出码

- `logs/environment/M0-03_<时间>_snapshot.json`：每次检查的独立快照，含版本、实际路径、GPU 输出和摄像头阶段日志。
- [reports/environment_check.md](../reports/environment_check.md)：最近一次检查的可读报告，每次更新。
- [reports/environment.md](../reports/environment.md)：人工维护的项目环境总报告，检查脚本不会覆盖它。

| 退出码 | 含义 |
| --- | --- |
| 0 | 训练检查通过，摄像头读到三帧并正常释放，M0-03 检查通过 |
| 1 | 训练检查或摄像头检查失败，查看报告 |
| 2 | 使用 `--skip-camera` 且训练检查通过；或命令参数非法，查看终端提示 |

`pip check` 与锁定版本比对用途不同：前者检查已安装包之间的声明依赖，后者检查项目实际选定版本。GPU 有限输出是功能证据，不是训练效果或性能基准；摄像头的 `reported_fps` 是设备属性，不是实测应用 FPS。

## 4. 2026-10-02 的实际结果与问题

| 检查 | 实际结果 |
| --- | --- |
| Python / 源码 / 依赖 / GPU | 通过；专用 Python 3.9.23，Ultralytics 8.4.171，torch 2.8.0+cu129，640×640 GPU 前向有限 |
| Windows 设备 | 识别 FHD USB camera，PnP 问题码 0，驱动提供者 Microsoft |
| 摄像头权限 | HKCU 与 HKLM 的 webcam ConsentStore 均为 Allow；该值不证明没有程序占用 |
| DSHOW 原生参数 | 实际读取三帧，`[480,640,3]` / uint8，像素最大值非零；在 `release()` 阶段超时 |
| MSMF 原生参数 | 能初始化，但读帧失败，出现 `can't grab frame` / `-2147483638` |
| 增加等待时间 | 两种后端 30 秒复查仍未完整通过 |
| MJPG / 640×480 请求 | 在参数设置阶段超时，没有解决问题 |
| MSMF 关闭硬件转换 | 读帧仍失败，没有解决问题 |
| OpenCV 4.10 对照 | 临时目录中的 4.10.0.84 也出现 DSHOW 释放超时、MSMF 读帧失败；本机项目 4.11.0.86 保持原版本 |

OpenCV 官方提供 `OPENCV_VIDEOIO_MSMF_ENABLE_HW_TRANSFORMS` 开关，控制 Media Foundation 图中的硬件转换；本次仅在诊断进程中设置为 0，未解决本机问题。[OpenCV 4.11 环境变量说明](https://docs.opencv.org/4.11.0/d6/dea/tutorial_env_reference.html)

已确认的是上述现象，尚不能确认根因是占用、驱动、USB 状态还是其他兼容性因素。需要先确认其他软件是否占用摄像头；若没有，重新拔插 USB 摄像头，并用 Windows“相机”确认能否正常显示和关闭，再复测。
