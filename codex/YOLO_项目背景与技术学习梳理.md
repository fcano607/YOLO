## 2. 项目任务与范围

目标：基于 YOLO11n-seg，完成杯子、瓶子、手机的摄像头实时检测与实例分割，并贯通数据准备、微调、结构对照、ONNX Runtime 独立推理、TensorRT 推理及实时显示。

| 项目类别 ID | 类别 |
| --- | --- |
| 0 | cup / 杯子 |
| 1 | bottle / 瓶子 |
| 2 | cell phone / 手机 |

该映射仅用于项目三类模型；COCO 预训练模型按其 `model.names` 查找对应类别。

每个目标的结果包含类别、置信度、检测框与独立掩膜。同一画面中的两个杯子应对应两个实例。当前数量指当前帧内预测实例数；跨帧身份跟踪、累计去重计数、行为识别和告警属于后续拓展。

## 3. 模型原理：从图像到多个实例

主链路：原图 → 预处理 → Backbone 特征提取 → 多尺度特征融合 → Segment 预测 → 置信度筛选与 NMS → 框和掩膜还原 → 显示与记录。

Backbone 逐步提取更抽象的特征；特征融合部分将不同分辨率的信息结合；Head 产生预测。官方 YAML 中 `head:` 区域也包含融合层，不能把该字段内的所有层都理解为最终预测头。

官方 YOLO11-seg 配置中，Segment 接收第 16、19、22 层的 P3/P4/P5 特征，对应下采样 8、16、32 倍；模型包含 C3k2、SPPF、C2PSA 等模块。[官方配置](https://raw.githubusercontent.com/ultralytics/ultralytics/main/ultralytics/cfg/models/11/yolo11-seg.yaml)

在方案的 640×640 输入下，三尺度位置数为 80² + 40² + 20² = 8400。这是候选位置数，不是画面中有 8400 个目标。

Segment 在检测预测之外生成原型掩膜和每个候选的掩膜系数；保留下来的实例用自己的系数组合共享原型。它并非为每个候选独立运行一套完整分割网络。[分割头源码参考](https://docs.ultralytics.com/reference/nn/modules/head/)

按方案设定，三类、32 个原型、batch=1、640 输入、无内置 NMS 的常规导出预期为：

- 候选张量：`[1, 39, 8400]`，39 = 4 个框参数 + 3 个类别分数 + 32 个掩膜系数。
- 原型张量：`[1, 32, 160, 160]`。
- NMS 后 K 个实例：系数矩阵 `A[K,32]` 与展平的原型 `P[32,25600]` 相乘，得到 K 张低分辨率掩膜 logits。

以上是方案下的预期形状，尚未本机运行验证。正式实现读取真实输出名、shape、dtype，并核查锁定版本的框编码与分数定义；不照搬 YOLOv5 的 objectness 乘法。

训练输出、普通推理输出与 export 输出的封装可能不同，需分别检查。原型通道数量也不等于类别数量。

## 4. 数据、标注与泛化证据

公共数据采用 COCO 2017 三类子集，自采数据覆盖桌面光照、距离、遮挡、背景、实物外观与姿态变化。方案建议公共训练约 1000–1200 张、自采约 300 张总量，均为起点而非已准备数量。

实例分割标签每行一个实例，格式为 `class_id x1 y1 ... xn yn`，坐标按图像宽高归一化，至少三个顶点；框标签不能替代真实轮廓标签。[官方标签格式](https://docs.ultralytics.com/datasets/segment/)

数据工作优先检查：类别重映射、标签遗漏、轮廓质量、真实空背景、多边形特殊情况、每类实例数和目标尺寸分布。被筛除的特殊实例若仍出现在图中，必须补标或处理该图，避免无意把目标当背景。

自采视频按拍摄组划分，避免连续近重复帧跨训练、验证、测试集合；结合实物和背景分组，检查测试组是否具备独立场景价值。冻结验证与测试清单，后续补样本主要进入训练池。

COCO 预训练模型可能已见过公共训练池图片，不能把这部分称为全新数据；自采独立测试组用于补充真实场景泛化证据。

## 5. 训练、评价与实验矩阵

训练需要理解分类、框回归、DFL 与分割损失各自约束什么，并结合实际日志定位问题；具体计算与权重以锁定版本为准。[官方损失源码参考](https://docs.ultralytics.com/reference/utils/loss/)

IoU 表示预测与真值的交并比；框 IoU 和掩膜 IoU 比较的对象不同。Precision 关注预测中正确的比例，Recall 关注真值中被找出的比例；mAP 综合置信度排序及匹配结果。mask mAP50-95 评估多个 IoU 阈值下的实例掩膜表现，是方案核心精度指标。

| 实验 | 模型与训练数据 | 要回答的问题 |
| --- | --- | --- |
| E0 | COCO 预训练模型，不做项目微调 | 初始效果如何，环境与导出是否可用？ |
| E1 | 原三类模型，公共训练池 | 三类微调基线表现如何？ |
| E2 | 原三类模型，公共 + 自采训练池 | 场景适配方案带来什么变化？ |
| E3 | 三类模型 + P3-SE，与 E2 相同数据 | 结构调整是否带来值得保留的收益？ |

E1/E2 数据量不同，也可能改变总优化步数，因此比较反映整体适配方案效果。若未来研究要隔离数据来源的作用，需另设匹配样本量、优化预算等对照。

E2/E3 是重点结构对照：保持划分、输入、训练预算、优化器、增强、初始化规则、种子与选权重规则一致。记录早停和实际训练量；不能只让 E3 从完成微调的 E2 权重继续训练。微小收益需要多种子复核。

验证集用于调参与选模型，测试集在方案确定后统一评估；公共和自采结果分开报告，并保留每类指标与失败案例。FPS 不能替代分割精度。

## 6. P3-SE 修改：假设与实现检查

SE 根据全局统计生成通道权重，对特征做通道重加权。[SE 原论文](https://arxiv.org/abs/1709.01507)

项目假设：在复杂桌面场景中，对高分辨率 P3 分支重加权可能改善识别和掩膜质量。此处是待验证假设；加入已有 SE 不能直接称为原创方法，也不能预先宣称提升。

方案在 Segment 前追加 SE，仅让 Segment 的 P3 输入经过它。原第 16 层供其他融合路径使用的连接保持原状；这与在第 16 层后整体插入并改变所有下游路径不同。

关键检查：

1. SE 保持输入输出形状一致；解析器传入实际通道数，自定义 YAML 明确 n 规模。
2. Segment 层由 23 移到 24 时，将可匹配的预训练分割头键对应映射，保存加载报告。
3. 三类输出的初始化与基线一致；核查共享层、原型层和系数层有没有意外漏加载。
4. 用真实小批量完成前向、反向和参数更新，确认 SE 梯度有效。
5. 正式训练前完成 ONNX 导出、ORT 执行与 TensorRT 兼容性检查。

最终是否部署 E3，由验证精度、速度与稳定性决定；负结果仍是有价值的对照记录。

## 7. 独立部署与一致性

ONNX 保存计算图与参数；ONNX Runtime 执行该图；TensorRT 根据图和目标环境构建、执行 engine。导出文件成功仅是部署链路中的一个步骤。

共享预处理保存原图尺寸、实际缩放和各侧补边：BGR → RGB → 等比例缩放与 letterbox → float32/255 → NCHW 连续张量。首版固定 batch=1、640×640、FP32、无内置 NMS。

共享后处理执行分数过滤、逐类别 NMS、候选与系数索引绑定、框还原、原型组合、去补边、掩膜缩放和阈值化。掩膜操作顺序、插值和整数舍入影响边界，应逐步核对参考实现。在线源码已存在阈值化和裁剪次序的实现细节变化，正式对齐以锁定 commit 为准。[官方掩膜处理](https://docs.ultralytics.com/reference/utils/ops/)

对齐顺序：相同输入张量 → raw 输出误差 → 相同后处理结果 → 自写后处理与官方参考结果 → 固定数据集评价。这样可区分图执行误差与后处理误差。

ONNX 后端以 ORT 执行模型，NumPy/OpenCV 处理结果；TensorRT 后端需实际管理 context、张量地址、GPU 内存、数据传输和执行。各后端向应用返回统一结果。

ORT CUDA 需核对 CUDA/cuDNN 兼容性及实际会话 provider；不能仅凭包名证明 GPU 已执行。[ORT CUDA 文档](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html)

TensorRT 先对齐 FP32，再验证低精度。11.x 已移除 `BuilderFlag.FP16`，采用强类型精度路线；不能无条件照搬旧构建示例。[官方迁移说明](https://docs.nvidia.com/deeplearning/tensorrt/latest/api/migration/tensorrt-10x-to-11x-python-api-reference.html)

方案的 ORT FP32 mask mAP 降幅不超过 0.5 个百分点、TensorRT FP16 不超过 1 个百分点，属于项目建议门槛，不是已测结果或平台保证。

## 8. 实时性能与系统验证

区分模型执行时间、包含预处理/传输/后处理的流水线时间、实际处理 FPS，以及采集到显示的画面延迟。GPU 异步执行需要正确同步或事件计时。

各后端使用同一模型、机器、输入、阈值和后处理，先预热，再记录 mean、p50、p95；CPU 与 GPU 结果单独解释。摄像头帧率可能掩盖推理加速，应另用固定图片序列或录制视频测速。

处理跟不上采集时，用最新帧缓冲限制积压；框、掩膜和显示图像必须属于同一帧。离线评价逐帧处理，不能套用实时丢帧规则。

稳定性检查包括连续运行、内存/显存趋势、空结果、多目标、相机异常、截图录像和资源释放。方案的 15–30 FPS、20–30 分钟运行检查均待硬件与实测确认。

## 9. 后续研究问题与推进顺序

已有方案首先支持三个问题：自采数据适配是否有效；P3-SE 是否改善质量且代价可接受；独立部署及低精度是否保持质量并提高实际处理效率。其价值需要由完整实验支持，当前尚无新颖性、优越性或发表结论。

后续如开展更深入研究，可在错误分析基础上考虑匹配预算的数据适配对照、SE 多种子与位置消融、目标尺寸/遮挡/光照分组表现、精度与延迟的权衡。上述是备选研究设计，不是新增的必做项目范围。

按原方案推进：环境检查与预训练闭环 → 当前模型源码和张量学习 → 数据及冻结划分 → E1/E2 基线与错误分析 → E3 修改与对照 → 独立 ONNX/TensorRT → 实时系统与报告。先学习当前网络，遇到具体问题再扩展版本和模块。

目录与命令以目录规划细化路径为准，例如 `artifacts/E2/best.pt`、`runs/train/`、`demo/input/fixed_benchmark.mp4`；完整方案中的简写路径和示例日期不代表现有文件或实验安排。

本聊天后续讨论应结合实际新增文件和实验记录更新判断，明确区分已验证结果、进行中的工作、方案参数和待验证假设。
