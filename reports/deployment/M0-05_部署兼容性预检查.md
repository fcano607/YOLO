## 2. 导出模型与实际接口

权重仍为官方 **80 类 COCO 预训练 YOLO11n-seg**，不是已经微调的三类模型。E0 的 cup=41、bottle=39、cell phone=67 是预测筛选映射；本次原始输出保留全部 80 类。

- 原始权重 SHA256：`55ed65c56c91713d23e8402371c6c49a6fd84f257f7dce452e8d70e41dcbe152`。
- 固定输入、batch=1、640×640、FP32、opset=17、dynamic=False、simplify=False、nms=False；未嵌入 NMS。
- 实际 ONNX 输入：`images [1,3,640,640]`，float32。
- 实际输出：`output0 [1,116,8400]`，116=4 个框坐标+80 个类别分数+32 个 mask 系数；`output1 [1,32,160,160]` 为分割原型。
- `onnx.checker.check_model(full_check=True)` 通过，IR=8；ONNX 文件约 11.2 MiB。
- TensorRT 原生 engine 本次约 15.5 MiB；输入和两个输出均为 float32，workspace 上限 1 GiB，关闭 TF32。通过 Python API 构建并执行，不依赖 `trtexec`。

模型与数组保存在本机 `artifacts/precheck/M0-05/`，未纳入 Git；文件哈希、版本与构建日志见[汇总证据](../../logs/deployment/M0-05_summary.json)。该 engine 没有 Ultralytics 自定义元数据头，应由本项目 TensorRT API 读取。

## 3. 同输入输出对照

使用 M0-04 已保存的公交车图、桌面图两张图片，不重新采集摄像头。先用锁定源码 LetterBox 固定到 640×640，再做 BGR→RGB、NCHW、float32、除以 255，保存输入及 PyTorch CUDA FP32 原始参考输出。每个后端读取同一份保存张量；汇总时核对 ONNX 与参考清单哈希一致。

预先固定逐元素判据：`|实际值-参考值| <= 0.001 + 0.0001 × |参考值|`，即 `atol=1e-3, rtol=1e-4`。两个输出都要求形状、float32 类型及有限值正确。

| 后端 | 两张图 output0 最大绝对差 | 两张图 output1 最大绝对差 | 超出容差元素数 | 实际执行证据 |
| --- | ---: | ---: | ---: | --- |
| ORT CPU | 0.00225830 | 0.00001836 | 0 | profile：912 次 CPU 节点执行事件 |
| ORT CUDA | 0.00271606 | 0.00002015 | 0 | profile：530 次 CUDA 节点执行事件，无 CPU 节点执行事件 |
| TensorRT FP32 | 0.00207520 | 0.00001895 | 0 | 反序列化 engine，以 GPU 张量地址执行 `execute_async_v3`，同步后回读两个输出 |

`output0` 同时包含不同尺度的坐标、分数与系数；大坐标的绝对差可能超过 0.001，但仍满足上述绝对+相对联合容差。节点事件数是这次两张图的 profile 记录，不是模型层数或测速指标。

ORT CPU/CUDA 与 TensorRT 工作进程均未导入 Ultralytics，未执行 PyTorch 模型。CUDA ORT 导入 torch 用于加载 CUDA/cuDNN DLL；TensorRT 使用 torch 分配 GPU 缓冲与管理 stream。两者尚未做到运行环境完全移除 torch。

完整数值：[CPU](../../logs/deployment/M0-05_ort_cpu.json)、[CUDA](../../logs/deployment/M0-05_ort_cuda.json)、[TensorRT](../../logs/deployment/M0-05_trt.json)。

## 4. 问题与处理

| 问题 | 处理与验证 |
| --- | --- |
| 继承的 TensorFlow 2.10 / TensorBoard 2.10 限制 protobuf<3.20，与 ONNX 要求冲突 | 经用户选择，从 yolo 移除这组组件，安装 protobuf 4.25.8；`pip check`、训练回归及 E0 回归通过；原 tf2 保留 |
| 最新包并非都支持 Python 3.9 | 按实际 cp39 Windows wheel 选择并固定 ONNX 1.17.0、ORT GPU 1.19.2、TensorRT CUDA 12 的 11.3.0.99 |
| TensorRT libs 在普通 PyPI 上为下载入口包 | 从 NVIDIA 官方索引下载 2,250,858,326 字节 Windows wheel，SHA256 与官方索引一致；bindings 和元包下载哈希也核对官方 PyPI |
| TensorRT `parse_from_file` 无法读取项目中文路径 | 保留[首次失败日志](../../logs/deployment/M0-05_trt_attempt1_unicode.log)，改用 Python 读取 ONNX bytes 后 `parser.parse(bytes)`；构建与执行通过 |
| TensorRT 11 API 与旧教程不同 | 使用强类型网络及 ONNX FP32 类型，清除 TF32 标志；未调用已移除的 FP16 构建标志 |

ORT 1.19 的 CUDA 12 / cuDNN 9 组合及先导入 torch 的 DLL 加载方式见 [ORT CUDA 官方说明](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html)。TensorRT 11 的强类型和精度 API 变化见 [NVIDIA 迁移指南](https://docs.nvidia.com/deeplearning/tensorrt/latest/api/migration/tensorrt-10x-to-11x.html)。ORT 的 provider 列表中出现 `TensorrtExecutionProvider` 不等于它可用；本次只验证 ORT CPU/CUDA 与直接 TensorRT API，未使用 ORT TensorRT EP。
